Run your own
Farcaster node
and client.

Set up a Snapchain read node and host your Farcaster client on the same AWS server. Read and post through your own node from your browser.

Start the setup ↓Understand the pieces

Start by reading a real post from your node. No Farcaster wallet is needed for that. You need a computer for setup; afterward, the client works on your phone too. AWS charges apply, and sync takes hours.

How the pieces connect

Farcaster is the network of accounts and signed social messages. Snapchain keeps those messages in sync. A client is the app you open to read and post; this guide shows you how to run your own.

This website

Explains the setup. It is hosted on Vercel and never connects to your node or asks for wallet keys.

Your computer

Runs the setup commands. After deployment, you can close the terminal and use the Farcaster client in a browser.

Your AWS server

Runs Snapchain and the client service. HTTPS connects your browser to the Farcaster client; the service reaches the node internally.

  1. Your browserAsk for casts
  2. HTTPSEncrypted connection
  3. Client serviceOn your EC2
  4. Your nodeReturn stored data

Try a real read: choose By FID, enter 3356280 and press Load feed. The request goes to your node; its stored casts come back along the same path. Reading does not need a wallet signature.

  1. Your browserSign your cast
  2. HTTPSEncrypted connection
  3. Client servicePass signed bytes
  4. Your nodeCheck and forward
  5. ValidatorsCommit a block

Real example: our test account posted a labelled verification cast through its own read node. Its app key signed the cast in the browser. Validators committed the message, and the node made the result readable. See the recorded cast hash.

  1. Validators commit the message
  2. Your node applies the block
  3. The Farcaster client shows confirmation

“Accepted for forwarding” only means the node received the signed message. The Farcaster client waits for a matching result before saying the action is confirmed.

  1. Download a snapshotFetch a recent copy of network state.
  2. Restore the databaseUnpack that copy onto your server’s disk.
  3. Catch up on blocksApply what happened after the snapshot.
  4. Keep followingApply new blocks as validators commit them.

Example: while your snapshot downloads, someone posts a new cast. That cast is newer than the saved copy. Catch-up brings the node forward so it can return newer posts too. Finishing the download is only the first stage.

A shard is a separate lane of the chain. ./relay status --verify checks that every reported shard is near the head and advancing, then reads a real cast. Check your node’s progress.

A read node can forward writes. It follows committed blocks but does not vote on them. Running one does not make you a validator or earn validator rewards. Read about node roles.

Before you start

Run the commands on your computer. The helper handles the new server.

Have three things ready: access to the source repository, an AWS account with billing enabled, and a computer where you can install tools. You do not need to create a server in the AWS dashboard first. If you are setting up a node for the first time, use New AWS server below.

Where do I type these commands?

A terminal is an app that runs text commands. On macOS, open Terminal from Applications → Utilities. On Linux, open your terminal app. On Windows, install WSL2 with Ubuntu, then open Ubuntu; run the guide’s commands there rather than in PowerShell. Install the required tools inside that same environment.

Paste one command, press Enter, and wait until the terminal is ready for another. Copy only the command, without adding a $ prompt. A browser address such as https://… goes in your browser; a command beginning ./relay goes in the terminal. Here, ./relay means “run the setup helper in this folder.”

  1. Install the local tools. Use macOS, Linux or WSL2. You need Git, Python 3.9+ and OpenSSH. Node.js is installed inside the server’s client build container; you do not need it locally for the hosted setup. The new-server path also needs AWS CLI v2 with your AWS account configured.
  2. Get repository access. The repository is private. Ask the owner for access before cloning. There is no public source download.

Check the tools in that same terminal before creating a server:

git --version
python3 --version
ssh -V
aws --version
aws sts get-caller-identity

The version commands should show Git, Python 3.9 or newer, OpenSSH and aws-cli/2. If you see “command not found,” install that tool using the links above, reopen your terminal and check again.

The last command should identify your intended AWS account. It does not create resources. Keep that output private. If it reports missing or expired credentials, finish AWS CLI configuration before continuing. Being signed into the AWS website alone does not sign in the terminal.

Which account or password do I use?

GitHub gives you access to the source code. A “Repository not found” message can mean you are not signed into an account with access. Open the repository link while signed in and resolve access before cloning again.

AWS pays for and manages the server. Follow AWS’s credential setup for your account; if an organization manages it, ask its administrator for the required permissions. Do not paste AWS credentials into this guide. A successful identity check confirms your login, not every permission needed to create resources.

The client login is generated later by the third command. It protects your hosted client and is separate from both AWS and your Farcaster wallet.

git clone https://github.com/vrajdesai78/farcaster-bounty.git
cd farcaster-bounty

After cloning, cd farcaster-bounty opens the downloaded project folder in your terminal. Keep this folder: it will also hold the saved server details and private SSH key in a hidden .relay-state directory. Do not delete it to retry setup or share it with someone else.

What will AWS create and charge for?

One Ubuntu 22.04 m5.xlarge server: 4 vCPU, 16 GB RAM and a 2,000 GiB encrypted gp3 disk at 3,000 IOPS / 125 MiB/s. The helper also creates an SSH key pair and security group. It uses an existing default VPC/subnet. It creates no NAT gateway, load balancer or paid monitoring.

You pay for compute, the full provisioned disk, public IPv4 and applicable transfer/taxes. Stopping the server leaves disk charges. No automatic shutdown is installed. Review the AWS calculator before provisioning.

Which AWS permissions and network access are needed?

EC2 is AWS’s name for a rented server. A security group is its firewall. SSH is the secure connection the helper uses to install software; normal setup does not require you to log into the server manually.

Your AWS identity needs EC2 describe, key-pair, security-group, instance-launch and tagging permissions, plus ssm:GetParameter to find Ubuntu’s public image. Cleanup needs stop/terminate and key-pair/security-group deletion permissions. The exact actions are listed in the repository’s SETUP.md.

SSH is restricted to your public IPv4 /32. Peer ports UDP 3382 and TCP 3383 are public. The node’s HTTP API and metrics stay on the server’s loopback interface. The setup helper opens TCP 80 and 443 for HTTPS during client installation on a managed server. AWS credentials stay on your computer.

Reading needs no Farcaster account. Posting needs a disposable FID with active account storage and its custody wallet. Owning a server does not create an account or pay for its storage.

Three commands

Use a new AWS server, or add the client beside a node you already run.

Run one command at a time, in order. Wait for each to finish before starting the next. Keep the same project folder if you return later.

Open checkip.amazonaws.com in another tab and paste the number shown, without spaces. Use your computer’s current connection, not the server’s IP. The added /32 permits SSH only from that address. This page only puts the value in your command.

Requires a node already running at /opt/snapchain. The node command only checks it. The client command installs the Farcaster client separately without replacing or restarting Snapchain. Existing hosts must allow inbound TCP 80 and 443. --remote-dir selects a different location.

  1. Create the server

    ./relay provision --ack-costs --ssh-cidr YOUR_IP/32

    Creates paid AWS resources in us-east-1 by default. Saves server details and the private SSH key in .relay-state/. Wait for “Host ready” before starting Snapchain.

  2. Start Snapchain

    ./relay node

    Installs Docker and starts the pinned node. Snapshot restore begins on the server. Wait for “Snapshot restore started,” then run the client command; you do not need to wait for full sync first.

  3. Start the client

    ./relay client

    Builds the client on your EC2 and prints its HTTPS URL. A free IP-based hostname is used by default. The login appears in your interactive terminal and is saved privately on your computer. Wait for “Hosted client ready,” then save the URL and generated login privately. Your terminal can close when installation finishes.

Run these from the repository folder on your computer.

Preview the plan before spending money

After filling in your IPv4, copy this command. The preview makes no AWS calls and creates nothing.

./relay provision --ack-costs --ssh-cidr YOUR_IP/32 --dry-run

To choose another AWS region or profile, add --region REGION or --profile PROFILE. Without a default subnet, supply --subnet-id SUBNET for an existing internet-routed subnet.

Wait for sync

A running container is not a synced node.

  1. DownloadGet snapshot chunks.
  2. RestoreDecompress and write the database.
  3. Catch upApply blocks created since the snapshot.

This can take hours. Quiet extraction logs can still mean work is progressing. Check bounded logs before restarting:

./relay logs

You can open the client while sync runs, but reads may fail until catch-up finishes. Leave the server running. From the same project folder, check readiness:

./relay status --verify
A successful sync check requires all three
CheckResult
Each shard’s blockDelayBelow 10 seconds in both samples
Each shard’s maxHeightAdvances across samples taken 15 seconds apart
Real queryA cast comes back from your node

When the command prints SYNC VERIFIED, continue to read your first cast. If it says the node is not near the head or the API is unavailable, check the logs for progress and try the check again later. Do not create a second server to fix a syncing first server.

Shards are separate lanes of the chain. Check every reported shard. The helper saves the result in .relay-state/sync-evidence.json. API errors during restore are possible; they do not establish whether restore is progressing.

Use the client

Open the HTTPS URL printed by the third command. Sign in, read a cast, then authorize a test account.

  1. Sign in to your hosted client. Open the URL printed by ./relay client. Use the generated login shown in your terminal. If it was not displayed, retrieve it locally with ./relay client --credentials. This server login is separate from your Farcaster wallet. Keep it private.
  2. Read casts. Choose By FID, enter 3356280 and load the labelled test casts. A cast is a Farcaster post. You should see our labelled test posts; that is your first successful read through your own node. You can stop here if you only want to read. Following combines recent casts from accounts followed by the entered FID, in chronological order.
  3. Authorize your test account. Choose Connect signer → Browser wallet. Use the custody wallet for your own FID with active storage. The next steps are optional and make public mainnet actions. Two wallet signatures approve a scoped app key. Adding this key is gasless; creating an FID and buying storage are separate paid steps.
  4. Post and read it back. Write “Testing my own Farcaster node.” The Farcaster client signs it in the browser, sends it to your node and waits for confirmation. Load your FID and check the cast appears.
  5. Try a reply, reaction and follow. Reply to your cast. Like it, then unlike it. Recast and undo. Follow a test target, check the result, then unfollow.
  6. Filter by app. Enter a requesting app’s FID and choose Include only or Exclude. With our self-authorized flow, use your own FID. Unknown or removed signer attribution is left out of filtered results.
  7. Revoke the test key. Forget clears this device’s session. Revoke cancels the key’s network authorization too. A revoked key should fail if imported again.

Vercel hosts this guide; your EC2 runs the client and node. The browser keeps your signing key in memory and sends signed actions over HTTPS. You can use the client after closing the setup terminal.

Do I need a domain or a local client?

The setup helper supplies a free sslip.io hostname based on the server’s public IPv4. Caddy obtains and renews its HTTPS certificate. This depends on public DNS and certificate-authority availability. A changed EC2 public IP needs an updated deployment URL.

For your own domain, point its A record to the server, then use ./relay client --domain client.example.com. For local development instead, install Node.js 22.12+ or a newer supported LTS and use ./relay client --local; that optional mode uses port 5173 and an SSH tunnel.

I need a new test account or already have a signer

The client authorizes an existing FID. Repository collaborators can follow SETUP.md → Optional new disposable account to create one separately. A new account needs ETH on OP Mainnet for registration and storage. Your node does not waive those costs.

Existing signer accepts a registered 32-byte Ed25519 app key. It is different from a custody-wallet private key. Prefer the browser wallet for authorization. The test recovery option is for a disposable account only. Enter a phrase only into software from developers you trust, after checking the code and the site you are using. Anyone with that phrase can control its wallet and any funds in it. Never enter a recovery phrase into this public guide.

Your account, keys and storage

Your FID identifies you. A wallet controls the account. An app key signs everyday actions. Your server runs the software.

  1. Custody walletApprove a new app key, its permissions and inactivity window.
  2. Your nodeForward the signed KEY_ADD and check the key becomes registered.
  3. App key in your browserSign casts, reactions and follows without another wallet prompt each time.

Real example: FID 3356280 authorized a separate app key, posted a cast and revoked the key afterward. The FID stayed the same throughout. This registration was gasless; no OP Mainnet transaction was needed for the app key.

The private app key is created and kept in your browser’s memory. Your wallet signs the permission; the server receives signed messages, not the wallet’s recovery phrase. Reloading forgets the local key. Revoking removes its network permission.

  1. Rent account storagePay through the protocol’s contracts on OP Mainnet.
  2. Your FID gets an allowanceSeparate limits apply to casts, follows and reactions.
  3. Use any clientThe same account limits apply in the Farcaster client and other apps.

Real node response, 21 October 2026: FID 3356280 reported CASTS: used 4, limit 100. That describes this account at this check; it is not a fixed quota for every user. Query your own FID for its current limits.

AWS disk is a separate bill. Its job is to hold the node’s database. Increasing the server’s 2,000 GiB disk does not buy more cast allowance for your FID. Registering an app key is gasless; purchasing account storage is separate.

Quick reference: FID, custody wallet, app key and storage
FID
Your permanent account number. Our disposable test account is 3356280. A username is its readable name and can change.
Custody wallet
The Ethereum account that controls your FID and approves app keys. Keep its secret separate from everyday posting.
App signer
An Ed25519 key allowed to perform specific social actions for your FID. New keys created by this client have a 24-hour inactivity window, refreshed when a signed message merges.
Storage rent
Pays for an FID’s allowance to keep social messages on the network. Casts, follows and reactions have separate limits. This is separate from the SSD you rent from AWS: a larger server disk gives your account no extra allowance.
Message and confirmation
A message is a signed action such as a cast, like or follow. Confirmation means it has appeared in committed network state. A successful submission response is only the first step.
What am I paying for with storage rent?

Storage is allocated to your FID, so the same allowance applies whichever client you use. It is not a gas fee charged for every cast. Storage purchases use the protocol’s contracts on OP Mainnet; authorizing a gasless app key is a separate operation.

Before writing or buying more, check your FID with GET /v1/storageLimitsByFid?fid=YOUR_FID on your node. The response reports used and limit for each message type, plus storage-unit details. For example, spare cast allowance does not tell you how much follow allowance remains. Check the current purchase price and any expiry terms rather than relying on an old quota or price table. Storage API reference.

How does a gasless signer work?

The custody wallet approves the key, its permitted actions, expiry window and nonce. A nonce is a sequence number that prevents an old authorization being reused. The requesting app also signs its identity. The Farcaster client submits KEY_ADD and checks the key is registered before using it.

In our flow, the user’s FID is also the requesting app FID. It is not a separate shared app identity. Reloading the client forgets its in-memory key; revocation changes network permission. Imported keys retain their existing permissions and expiry.

If a step fails

Keep the error and your saved state. Check the cause before repeating a paid step.

The terminal says “No such file” or cannot find the Farcaster client

Open the project folder in your terminal before running ./relay. If you opened a new terminal window, use cd followed by the path to your existing farcaster-bounty folder. Do not clone another copy or delete saved state to retry. “Command not found” for git, python3 or aws means that tool needs installing or is not available in this terminal environment.

SSH will not connect

Check the instance is running, the local key exists and port 22 allows your current public IPv4 /32. If your address changed, update that rule in AWS. Do not open SSH to the entire internet. A local sandbox restriction needs local network permission; it does not prove the server is down.

Provisioning was interrupted

Rerun the same command from the same repository folder. .relay-state records the resources and launch token. Keep it: deleting it can leave paid resources behind. Inspect AWS before starting a separate deployment.

The API resets or sync looks stuck

Check ./relay logs, free disk and restore activity. Downloading and unpacking are different stages. Avoid restarting a progressing restore. The read-node mempoolSize value 4294967295 means “not reported,” not billions of pending posts.

A local development port is already in use

Stop the client or tunnel you previously started, or use different ports:

RELAY_TUNNEL_PORT=13382 PORT=5175 ./relay client --local

Then open http://127.0.0.1:5175/. The setup helper refuses to replace an unrelated process.

HTTPS or the hosted client is unavailable

Check DNS points to the server and inbound TCP 80 and 443 are allowed. On an existing host, you manage those firewall rules. The installer reports success only after a valid HTTPS health check. If a certificate is still pending, keep saved state, check Caddy logs and rerun ./relay client.

On the server, inspect sudo docker compose -p relay-client -f /opt/relay-client/compose.yml logs --tail 40. Do not restart Snapchain to fix client hosting. The optional custom domain needs an A record pointing to the server.

Signer authorization fails or a post stays pending

Check the FID’s custody wallet, active storage and current signer state. An expired or revoked key cannot post. Acceptance by a read node does not guarantee inclusion: it forwards the message through gossip and keeps no pending-message queue. The Farcaster client checks confirmation and resends identical signed bytes at most twice. Inspect the result before creating a duplicate action.

Stop and clean up

Manage the client, compute and disk separately.

Closing your browser leaves the server running and charges continuing. If you authorized a test app key, revoke it in the Farcaster client before stopping the server.

For a server created by the setup helper, preview either action first:

CommandConsequence after confirmation
./relay stopStops compute. The disk remains and still costs money.
./relay destroyPermanently deletes the managed instance and configured root disk, then removes its recorded security group and AWS key pair.

Use the same terminal and project folder as setup. Do not run destroy if you want to keep the node or its data.

The preview makes no change. To act, repeat it with --confirm INSTANCE_ID using the exact ID printed. Save any data you want to keep before deletion. Check AWS afterward for retained disks, snapshots or partial cleanup failures.

Stop only the hosted client (advanced)

This leaves Snapchain and the paid server running. If you already use SSH to access your server, run this command there, rather than in your computer’s local project folder:

sudo docker compose -p relay-client -f /opt/relay-client/compose.yml stop

There is no automatic shutdown or deletion. EC2 and disk charges continue after stopping only the client. For optional local mode, Ctrl-C stops the local client and ./relay disconnect closes its tunnel. Servers connected through Existing node are never stopped or destroyed by the setup helper.
