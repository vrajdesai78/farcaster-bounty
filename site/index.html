Run your own Farcaster node and client

Set up a Snapchain read node on AWS, connect a browser client to it, and check that you can read and publish through your own server.

Updated 23 October 2026 · Snapchain 0.14.3 · macOS, Linux or Windows with WSL2

Most of the time, you use Farcaster through someone else’s app and infrastructure. Here, we will run the app and its node ourselves. By the end, you will have an HTTPS address you can open on your phone, a local copy of Farcaster’s messages on your server, and a way to verify where your reads and writes go.

You can follow the reading steps without a Farcaster account. To publish, you will need an existing account with storage and access to its custody wallet. We will get to those terms when we reach posting.

Start here

You will use two computers: your own laptop for the setup commands, and a rented computer at Amazon Web Services (AWS) to keep the node running. You do not need to rent or configure that server by hand; the setup program in this guide does that.

We will first get the setup program onto your laptop. Then we will use it to create the server, install Snapchain and start the Farcaster client. After the node has caught up with the network, you can open the client in a browser and read a feed.

Check the cost before starting. The server uses 4 virtual CPUs, 16 GB of memory and a 2,000 GiB disk. AWS charges for the rented computer, disk, public IP address and applicable transfer. Check the AWS calculator for an m5.xlarge instance and 2,000 GiB gp3 disk in us-east-1. Sync can take many hours or run overnight. Nothing shuts down automatically.

The setup program and this guide are open source under the MIT license. Anyone can download and use them. You do not need a GitHub account or an invitation.

Start with step 1 and work down the page. Run each command separately and check its result before continuing. Reading needs no Farcaster account; posting later is optional.

Already have the files and tools? Three-command overview

This is a shortcut for readers who have completed step 1. Run these separately from the downloaded farcaster-bounty folder, replacing YOUR_IP with your public IPv4 address. The first command starts AWS billing. Step 2 explains each command and supplies a command builder.

./relay provision --ack-costs --ssh-cidr YOUR_IP/32

What we’re running

Farcaster is the social network: accounts, casts, replies, reactions and follows. These actions are signed messages, so a different client can recognize the same account and read the same public data.

Snapchain stores and orders those messages. Validators agree on blocks of messages. Our read node follows those blocks and maintains a database we can query. Despite the name, a read node can also forward signed writes to validators. It does not vote on blocks or earn validator rewards. See validators and read nodes.

The Farcaster client is the website we will use to read and post. It runs beside Snapchain on the AWS server. Your browser reaches the client over HTTPS; the client reaches the node on that same machine. You will run setup commands on your computer, but the server keeps working after you close the terminal.

1. Get the setup program onto your computer

1a. Get the source

The MIT-licensed source is public. You can clone it without a GitHub account. The download commands are in step 1d below, after the tool and AWS checks.

1b. Check the prerequisites

Use macOS, Linux or Ubuntu in WSL2. Install these tools in that environment:

  • Git.
  • Python 3.9 or newer.
  • OpenSSH.
  • AWS CLI v2.

Run each line separately:

git --version
python3 --version
ssh -V
aws --version

Each should print a version. Python must be at least 3.9, and AWS should include aws-cli/2. If you see “command not found”, return to that tool’s installation instructions before continuing. Node.js and Docker are installed or used on the server; you do not need to install them on your laptop for this setup.

1c. Connect your AWS account

If you do not have an AWS account, create one at AWS. Then follow AWS’s command-line sign-in instructions for your account. Account types use different sign-in methods; logging in to the AWS website alone is not enough.

Check the terminal login:

aws sts get-caller-identity

You should see fields named Account and Arn. Confirm this is the account you intend to pay with. If it reports missing credentials, expired login or denied access, finish the AWS sign-in instructions before proceeding. If someone else manages the account, ask them for the EC2 permissions listed below.

1d. Download the setup files

In the same terminal, run:

git clone https://github.com/vrajdesai78/farcaster-bounty.git

This downloads the files into a folder named farcaster-bounty under the terminal’s current location. Wait for Git to finish downloading, then enter that folder:

cd farcaster-bounty

If the destination already exists, use your existing project folder instead of cloning a second copy.

Check that the setup program runs:

./relay --help

You should see output beginning usage: relay, followed by commands such as provision, node and client. This check is free and creates no server. The relay script is the setup helper included with this project.

Keep this terminal in this folder for the rest of the guide. The program will save your server details and SSH key in a hidden .relay-state folder here. Keep that folder so you can resume setup and delete the same server later. If you open a new terminal, return to the downloaded project folder before running a command.

Which AWS resources and permissions are needed?

The managed setup creates one Ubuntu 22.04 m5.xlarge instance (4 vCPU, 16 GB RAM), a 2,000 GiB encrypted gp3 disk (3,000 IOPS, 125 MiB/s), an SSH key pair and a security group—a set of network access rules. It uses an existing default VPC and subnet, AWS’s network for your server; it creates no NAT gateway, load balancer or paid monitoring.

Your AWS login needs to describe EC2 resources, create key pairs and security groups, launch and tag instances, and read ssm:GetParameter to find the Ubuntu image. Cleanup needs stop, terminate and delete permissions. SETUP.md in the downloaded folder lists the actions.

SSH on port 22 is restricted to your IP. UDP 3382 and TCP 3383 are public for Snapchain, as are 80 and 443 for the website. HTTP API port 3381 and metrics bind to the server’s loopback interface; the gRPC API on TCP 3383 is public. Your AWS credentials remain on your computer.

2. Create the server and install the software

We will create a server, start Snapchain, then install the client beside it. Keep using the terminal from step 1, inside the downloaded farcaster-bounty folder. You should already have seen usage: relay from the help check. If not, complete step 1 first. Run the three commands below one at a time.

Open checkip.amazonaws.com and paste the number it shows into this field to fill in your command. SSH is the secure connection used to install the software; only this IP will be allowed to connect. This form stays in your browser and does not run commands or send your IP to us.

Expects Snapchain at /opt/snapchain; use --remote-dir if yours lives elsewhere. Your node is left alone: the client installs beside it. Open inbound TCP 80 and 443 yourself.

For a new server, fill in your public IP above. provision means “create the cloud resources”. --ack-costs confirms that you understand they cost money. --ssh-cidr sets the allowed SSH source; the /32 means this one IPv4 address. Copying a command only copies text—you still need to paste it into your terminal and press Enter.

  1. Create the server

    ./relay provision --ack-costs --ssh-cidr YOUR_IP/32

    Creates the server in us-east-1 and saves its details in .relay-state/. AWS billing starts here. Wait for “Host ready:” and for your terminal prompt to return.

  2. Start Snapchain

    ./relay node

    Installs Docker, starts the node and begins the snapshot restore. After “Snapshot restore started”, you can install the client while the node restores in the background.

  3. Start the client

    ./relay client

    Builds the client on the server and prints its HTTPS address and a login. Wait for “Hosted client ready”, then save both somewhere private. You can close the terminal now.

Run these on your computer, inside the downloaded farcaster-bounty folder.

Preview the plan before paying

Fill in your IP above, then run this. It shows what would be created without touching AWS.

./relay provision --ack-costs --ssh-cidr YOUR_IP/32 --dry-run

Add --region REGION or --profile PROFILE to change region or AWS profile. If your account has no default subnet, pass --subnet-id SUBNET.

At this point, the website can be up while the node is still restoring. That is expected. The next step checks whether the database is ready to use.

3. Wait for sync and verify a read

Leave the server running. Sync can take many hours or run overnight; download speed, disk performance and the snapshot size all affect the wait. A running container alone does not tell you that sync is complete.

A new node needs a copy of Farcaster’s messages. It downloads a snapshot, unpacks it into its database, then applies the blocks created since that snapshot. Each shard—a separate lane of the chain—must catch up.

The logs can go quiet while it unpacks; that's normal. To see what it's doing:

./relay logs

You can open the client in the meantime, but reads may fail. When you think it's done, check:

./relay status --verify
It takes two samples, 15 seconds apart, and passes when
CheckPasses when
Every shard's blockDelayUnder 10 seconds in both samples
Every shard's maxHeightHigher in the second sample
A real readYour node returns a cast

When it prints SYNC VERIFIED, go to step 4. If not, check the logs and try again later. If restore is progressing, leave it alone. Restarting can interrupt the work; creating another server adds another bill. The result is saved in .relay-state/sync-evidence.json, inside the project folder on your computer.

4. Use your Farcaster client

Open the HTTPS address printed by ./relay client, on your computer or phone. You are now running your own Farcaster client: the interface and the node behind it are on your server.

To install the client on your phone, open this HTTPS address and choose Install app. On iPhone or iPad, use Safari’s Share → Add to Home Screen. The installed app uses the same server and login; the node keeps running on EC2. Account signing keys stay in memory, so reconnect after closing or reloading the app.

Read a real account from your node

  1. Sign in with the login from step 2. Lost it? ./relay client --credentials prints it again. This login only protects your client; it has nothing to do with your Farcaster wallet.
  2. Read a feed. FID is an account’s permanent number. Choose By FID, enter 3356280 and press Load feed. Our labelled test casts appear, read from your own node. Switch to Following to see recent casts from accounts that FID follows. If you only wanted to read, you're done.

For example, when you load FID 3356280, the browser asks your client for that account’s casts. The client reads your Snapchain database and returns them. No third-party social API key is involved. The Following view collects recent casts from a bounded set of followed accounts; it is not a complete or ranked feed.

Before posting: your account and its app key

Reading needed no Farcaster account. Posting does: the network must know whose message this is and whether the key signing it has permission.

FID
Your account number, such as 3356280. Your username points to it and can change; the FID can't.
Custody wallet
The Ethereum wallet that owns the FID. You use it to authorize an app key; it also controls account ownership.
App key
A key your browser creates to sign casts, likes and follows. It can only do what the wallet allowed. New keys registered here have a 24-hour sliding expiry, refreshed whenever a message they sign is merged. Imported keys keep their existing permissions and expiry.
Storage
Paid onchain per FID. It sets how many casts, likes and follows the network keeps for you, in every client.

Think of the custody wallet as the account owner, and the app key as permission to use certain features. Here, the browser asks the custody wallet for two signatures to register a gasless app key. The app key then signs casts, reactions and follows within its allowed scopes. It cannot change who owns your FID.

Approving a key is free; no gas. Creating an FID and buying account storage are separate onchain actions on OP Mainnet and cost ETH. Both private keys stay in your browser and wallet; the server receives signed messages.

Why account storage and server storage are different

Your AWS disk holds a copy of the network’s database. Account storage rent sets how many messages the network keeps for your FID, across all clients. Paying for more AWS disk does not increase your account’s message allowance.

For a real example, on 21 October 2026 our test FID reported CASTS: used 4, limit 100. That is an observation for this account, not a universal quota. Read yours with GET /v1/storageLimitsByFid?fid=YOUR_FID on your node. See the storage API reference.

What is inside a gasless key approval?

The wallet approves the app key, its allowed message types, its expiry window and a nonce—a counter that prevents replaying an old approval. The requesting app signs too; this client uses your own FID for that role. The browser submits a KEY_ADD message and waits for network confirmation. The Snapchain writing guide explains the message format.

Publish a test cast

The steps below are optional and post publicly on Farcaster. Use an account you're happy to test with: one that already has an FID and storage.

  1. Connect your account. Choose Connect signer → Browser wallet and pick the FID's custody wallet. You’ll sign two approvals to register an app key, without paying gas.
  2. Post a cast. Try “Testing my own Farcaster node.” The client shows Confirmed once the network has it. Load your FID to see it in your feed.
  3. Try the rest. Reply to your cast, like and unlike it, recast and undo, then follow and unfollow someone.
  4. Filter by app. Enter an app's FID and choose Include only or Exclude. In this client, the app FID is your own FID. Casts whose app attribution cannot be resolved are left out. Attribution for revoked keys may no longer be available.
  5. Revoke the key. Forget clears the key from this browser. Revoke removes it from the network, so it can't post again.

“Accepted” is only the first hop. Your read node forwards the signed message to validators, which commit it in a block. Your node then applies the block. The client waits for that committed result before showing “Confirmed”. Read nodes forward writes on a best-effort basis; they do not keep a mempool of pending posts.

Use my own domain, or run the client locally

By default you get a free sslip.io address based on the server's IP, with HTTPS from Caddy. Stopping and starting the server can change its public IP, and with it this address.

For your own domain, point an A record at the server and run ./relay client --domain client.example.com. To run the client on your computer instead, install Node.js 22.12+ and run ./relay client --local. It uses port 5173 and an SSH tunnel to the node.

I don't have a test account, or I already have an app key

The client needs an existing FID. You can follow “Optional new disposable account” in SETUP.md. A new account needs ETH on OP Mainnet for registration and storage; running a node doesn't cover that.

Existing signer takes a registered 32-byte Ed25519 app key, which is not your wallet's private key. Prefer Browser wallet. The recovery phrase option is for throwaway test accounts only: anyone with the phrase controls the wallet. Only enter a recovery phrase into software from developers you trust. Never enter it into this guide.

5. Stop or delete the server

Revoke any test app key first (step 4). Then, from the project folder:

CommandWhat it does
./relay stopStops the server. The disk stays, and so does its bill.
./relay destroyDeletes the server, its disk, security group and key pair. This can't be undone.

Both commands only preview at first. To go ahead, run the same command again with --confirm INSTANCE_ID, using the ID from the preview. After destroying, check AWS for leftover disks or snapshots.

Stop only the client

The node and the server keep running and billing. Run this on the server over SSH, not on your computer:

sudo docker compose -p relay-client -f /opt/relay-client/compose.yml stop

If you used I already run a node, the helper never stops or deletes that server. For local mode, press Ctrl-C to stop the client and run ./relay disconnect to close the tunnel.

Troubleshooting

“No such file” or “command not found”

Your terminal isn't in the project folder. cd into your existing farcaster-bounty folder; don't clone a second copy. If git, python3 or aws is missing, install it in the same terminal environment (WSL2 on Windows).

SSH won't connect

Check that the server is running and that its security group allows port 22 from your current IP. If your IP has changed, open EC2 → Security Groups, select this server’s group, and edit its inbound SSH rule to your new public IPv4 address followed by /32. Keep port 22 limited to that address. Editing the rule requires ec2:ModifySecurityGroupRules permission.

Setup was interrupted

Run the same command again from the same folder. .relay-state remembers what was already created, so it picks up where it stopped instead of creating a second server.

Sync looks stuck, or the API keeps resetting

Check ./relay logs and free disk space. Downloading and unpacking are separate stages, and unpacking can be quiet for a long time. Don't restart a restore that's still making progress. A mempoolSize of 4294967295 just means “not reported”.

The client's HTTPS address doesn't load

Check that ports 80 and 443 are open and, with a custom domain, that its A record points to the server. If the certificate is still pending, wait a bit and run ./relay client again.

To see the client's logs, run sudo docker compose -p relay-client -f /opt/relay-client/compose.yml logs --tail 40 on the server. Don't restart Snapchain to fix the client.

Approving a key fails, or a post stays pending

Check that you used the FID's custody wallet, that the FID has storage, and that the key hasn't expired or been revoked. A read node passes posts on but doesn't queue them, so the client resends the same signed post up to twice. Load your feed before posting again, so you don't post twice.

A local port is already in use

Stop the earlier client or tunnel, or pick other ports:

RELAY_TUNNEL_PORT=13382 PORT=5175 ./relay client --local

Then open http://127.0.0.1:5175/.
